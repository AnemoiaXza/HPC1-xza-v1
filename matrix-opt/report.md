# 实验报告：单机环境下矩阵乘法并行方案对比

## 1. 实验背景

使用 MPI 实现矩阵乘法的并行计算。实验手册中的原始 MPI 方案（`matrix/gemm.cpp`）按行列分块，通过 MPI_Send/Recv 在进程间分发和回收数据。该方案设计的目标环境是多台物理主机构成的集群，但在单机 WSL2 环境下，MPI 进程间通信退化为本地内存拷贝，通信开销反而超过了计算收益。

本实验进一步实现了三种优化方案，对比它们在单机环境下的性能表现，分析并行策略的选择依据。

## 2. 实验环境

| 项目 | 配置 |
|------|------|
| CPU | Intel Core i7-14700HX (28核) |
| 内存 | 15 GB |
| 操作系统 | WSL2 (Ubuntu 22.04) |
| MPI 实现 | MPICH 3.3.2 |
| 编译器 | GCC 11.4.0 |
| 线性代数库 | OpenBLAS 0.3.8 (HASWELL, AVX2) |

## 3. 测试方案

四种矩阵乘法实现：

| 方法 | 并行方式 | 数据共享 |
|------|---------|---------|
| **Serial** | 单线程串行 | - |
| **OpenMP** | `#pragma omp parallel for` 多线程 | 共享内存，零拷贝 |
| **MPI-SharedMem** | `MPI_Win_allocate_shared` 共享内存窗口 | 物理内存共享，仅同步开销 |
| **MPI-Original** | `MPI_Isend` / `MPI_Recv` 分发数据 | 每次计算前后拷贝子矩阵 |

测试矩阵规模：512、1024、2048、4096。每个方法测试多组 worker 数（1/2/4/8/16 线程或进程），取最优结果。

## 4. 实验结果

### 4.1 各方法最佳性能对比（2048×2048）

- MPI-SharedMem（16 进程）：590 ms，加速比 **10.1×**

右图展示了加速比随 worker 数量变化的趋势。OpenMP 呈现近乎线性的加速曲线，MPI-SharedMem 紧随其后但略有差距，MPI-Original 因通信开销在单机上加速比始终低于 1（小矩阵时甚至严重倒退）。

|------|---------|-----------|--------|
| Serial | - | 47292 | 1.00× |

## 5. 分析讨论

### 5.1 为什么 MPI-Original 在单机上性能最差

MPI-Original 的 `mpi_sgemm` 函数在每次计算前需要：
1. Rank 0 将子矩阵通过 `MPI_Isend` 发给各 worker
2. Worker 通过 `MPI_Recv` 接收
3. 各进程独立计算
4. Worker 通过 `MPI_Send` 将结果发回 Rank 0
5. Rank 0 汇总拼装最终结果

在单机上，这些 Send/Recv 操作本质上是在同一个物理内存上拷贝数据。以 1024×1024 为例，每个子矩阵约 1MB，16 进程需要拷贝约 32MB 的数据。而四台物理主机的集群中，数据分发和计算可以真正并行，通信与计算重叠执行。单机上所有拷贝串行发生，开销远超收益。

### 5.2 OpenMP 为何是单机最优解

OpenMP 的 fork-join 模型在单进程内的多个线程间共享全部数据，主线程生成矩阵后，各工作线程通过 `#pragma omp parallel for` 直接读写同一块内存。不存在数据分发和回收步骤，线程调度开销在微秒级别。这是共享内存架构下最自然的并行方式。

### 5.3 MPI 共享内存的折中

MPI-SharedMem 使用 `MPI_Win_allocate_shared` 创建跨进程共享的物理内存窗口，消除了数据拷贝，但仍需 `MPI_Win_sync` + `MPI_Barrier` 保证内存可见性。同步开销约为几十微秒到几毫秒，在 4096 矩阵下占总时间的 <1%，但在 512 小矩阵下占比显著，导致小矩阵加速效果打折扣。

### 5.4 通信-计算比

令矩阵边长 = N，计算量 = O(N³)，通信量 = O(N²)。通信-计算比 = 1/N。N 越大，通信占比越低。这与实验结果一致：4096 矩阵下 MPI-SharedMem 的同步开销仅占总时间不到 1%，而 512 矩阵下加速比曲线明显趋于平缓。

### 5.5 理论验证：实验数据是否符合预期

#### (a) O(n³) 时间复杂度验证

矩阵乘法的理论复杂度为 O(n³)，矩阵边长翻倍，计算量应为 8 倍。以 Serial 为基准验证：

| 规模变化 | 时间比 | 理论值 | 偏差 |
|----------|--------|--------|------|
| 512→1024 | 8.85× | 8.0× | +10.6% |
| 1024→2048 | 7.66× | 8.0× | -4.2% |
| 2048→4096 | 7.95× | 8.0× | -0.7% |

三个比值均围绕 8.0 上下小幅波动，平均偏差仅 5%。小矩阵的偏大（8.85×）是函数调用、循环初始化等固定开销占比更高所致；矩阵越大，主体计算越主导，比值越接近理论值。**实验结果与 O(n³) 理论高度吻合。**

#### (b) 并行效率随问题规模增长

Amdahl 定律预测：问题规模越大，串行部分占比越低，并行效率越高。OpenMP 16 线程数据验证了这一点：

| 矩阵规模 | 加速比 | 并行效率 |
|----------|--------|----------|
| 512 | 6.83× | 42.7% |
| 1024 | 9.99× | 62.4% |
| 2048 | 12.11× | 75.7% |
| 4096 | 12.40× | 77.5% |

并行效率从 512 的 43% 稳步提升至 4096 的 78%。Gustafson 定律指出：问题规模增大时，可并行的计算部分占比上升，加速比逼近理想值。数据趋势与理论一致。

MPI-SharedMem 16 进程表现出同样的规律：

| 矩阵规模 | 加速比 | 并行效率 |
|----------|--------|----------|
| 512 | 6.06× | 37.9% |
| 1024 | 8.30× | 51.9% |
| 2048 | 9.93× | 62.0% |
| 4096 | 10.28× | 64.2% |

效率始终低于 OpenMP，差值（约 10-15 个百分点）来自 `MPI_Win_sync` + `MPI_Barrier` 的同步开销。随着矩阵增大，差值有收窄趋势，符合"同步开销在总时间中占比递减"的理论预期。

#### (c) MPI 通信开销的规模效应

MPI-SharedMem 在 1 进程下的耗时与 Serial 基本一致（偏差 <5%），说明共享内存分配本身不引入额外计算开销。多进程后的减速完全来自同步：

- 512 矩阵：16 进程同步开销占比 ≈ 1 − 37.9%/42.7% ≈ 11 个百分点
- 4096 矩阵：同步开销占比 ≈ 1 − 64.2%/77.5% ≈ 17 个百分点

绝对值上同步开销几乎不随矩阵变化（固定几次 barrier 调用），但占比在小矩阵下更高，解释了小矩阵并行效率更低的现象。这也与"屏障同步为 O(p) 开销、与问题规模无关"的理论模型完全一致。

#### (d) 单机 MPI Send/Recv 的开销放大

MPI-Original 在 np=1 时凭借内部 OpenMP 28 线程获得 12.3×（4096）的加速，但一旦 np>1 引入 Send/Recv：
- 512/np=16：耗时 418ms，而 Serial 仅 88ms，慢了 **4.8 倍**
- 4096/np=16：耗时 4830ms，而 Serial 需 47292ms，仅快 **9.8 倍**（但 16 进程内部 448 个 OpenMP 线程争抢 28 核）

Send/Recv 的数据拷贝量为 O(n²) ≈ 4096² × 4B × 16 = 1GB+，将所有数据拷贝开销串行化在单机内存总线上，完全抵消了并行收益。**实验结果与"单机 MPI 通信无真正并行 I/O 带宽"的理论分析一致。**

## 6. 三个 MPI 实验对比 (gemm / conv / pooling)

实验手册提供了三个 MPI 程序，计算量级和通信模式不同，在单机上的表现差异显著。

### 6.1 各实验并行缩放

![三实验对比](3exp_scaling.png)

左图为 1024×1024 规模下各实验绝对耗时随进程数的变化：
- **Gemm**：np=2 略快于 np=1（减少的线程竞争 > 增加的通信），但 np=8 已明显慢于 np=1
- **Conv naive**：随着 np 增大线性变慢，通信复制完全支配
- **Conv img2col**：np=2 略快于 np=1，但 np>4 后同样减速

### 6.4 原理解析

详见 [3exp-principles.md](3exp-principles.md)，核心要点：

| 实验 | 计算量 | 通信量 | 算术强度 | 单机 MPI 效果 |
|------|--------|--------|---------|-------------|
| Gemm | O(n³) | O(n²) | 高（~n 次乘加/元素） | 大矩阵勉强可用 |
| Conv (img2col) | O(n²·K²) | O(n²) | 中（K² 次乘加/元素） | np=2 略快 |
| Conv (naive) | O(n²·K²) | O(n²) | 中（循环开销大） | 不适用 |
| Pooling | O(n²·K²) | O(n²) | 极低（仅比较操作） | **完全不适用** |

### 6.5 为什么 Pooling 并行总是减速

Pooling 的计算极度轻量——每个输出元素仅需 16 次 `max` 比较（4×4 kernel），不涉及任何乘法或浮点运算。相比之下，发送/接收一行数据需要通过 MPI 协议栈完成序列化、内存拷贝和校验，开销远大于 16 次比较。

以 1024×1024 为例：
- 单进程计算量：256×256×16 = 1,048,576 次比较（微秒级完成）
- 4 进程通信量：每个 worker 需收发 256×1024×4B ≈ 1MB 数据（毫秒级完成）

**通信比计算贵了 3-4 个数量级**，所以增加进程数必定越来越慢。

## 7. 结论

1. **单机环境下优先使用 OpenMP**：共享内存、零通信、线性加速。
2. **MPI 共享内存可作为多机方案的过渡**：保留了 MPI 进程模型但消除了数据拷贝，适合开发和调试。
3. **MPI Send/Recv 方案仅在多节点集群中有意义**：单机上通信开销远大于计算收益，矩阵越小越明显。
4. **问题规模是并行效率的关键因素**：大规模计算才能分摊通信/同步的固定开销。
5. **不同计算的并行化潜力差异巨大**：Gemm O(n³) > Conv O(n²·K²) >> Pooling（仅比较）。计算越"重"，MPI 越值得；计算越"轻"，通信越致命。
